# Issue 80: reject silently ignored declaration options

decision: Work milestone issues sequentially; #80 starts only after #77 merged and its worktree was removed.
decision: Claude owns repository research and implementation heavy lifting through Tractor; root owns contract decisions, review, proof, and merge.
correction: Do not design validation against antagonistic or deliberately bogus declarations. Assume coding agents configure supported syntax honestly; reject real recognized-but-unapplied options because they silently corrupt intended artifacts.

proof: Reproduced the confirmed case live via a throwaway scratch module (built ./gen-jsonschema, ran it against `WithEnum(Thing{}.PL)` where PL is `*Level`): schema-only exits 0 and emits `"pl":{"type":"integer"}` with no enum; adding `-typescript` on the identical fixture exits 1 with "field Thing.PL enum registration requires a direct named enum type at .../types.go:14:5". Full findings and proposed fix in ephemeral/issue-80/research.md.
finding: Root cause is `resolveEnumFieldPlan` (internal/builder/gen_schema.go:1019-1025) — when the field's type isn't a direct `*dst.Ident` after Optional[E]/Nullable[E] unwrapping (a bare `*Level` is never unwrapped; `Wrapper()` only recognizes the two generic wrappers, internal/syntax/node_wrappers.go:657-666), the `WithStringerEnum` branch errors but the plain `WithEnum` branch does `return nil, nil`, which the caller (`resolveLocalEnumFields`) treats as "field not eligible, skip silently." TypeScript's independent implementation of the same check (`internal/builder/typegrammar.go:341-348`, `fieldValue`) has no stringer/non-stringer split and errors unconditionally — that's the whole asymmetry.
finding: Scope-checked every other recognized option kind the scanner produces (WithFunction, WithStructAccessorMethod, WithStructFunctionMethod, WithRenderProviders, AsRef, WithDiscriminator, WithInterface, Impl, WithInterfaceImpls, WithStringerEnum) against their consumers in gen_schema.go; none has an analogous silent-drop path today (interface field-owner resolution already errors on non-direct field types; provider FieldName only exists because the registration selector expression `Owner{}.Field` requires it to compile; AsRef/WithRenderProviders funnel into structures shared identically by both generation paths). The plain `WithEnum` non-stringer branch is the only confirmed instance — did not generalize the fix beyond it.
decision: `internal/builder.New()` (called unconditionally at builder.go:64, before RenderSchemas/RenderGoCode/TypeScript apply) is already the earliest shared validation point for both generation paths; no new validation phase or ordering change is needed. The bounded fix is one branch in `resolveEnumFieldPlan` returning the existing WithStringerEnum-style `fmt.Errorf` instead of `nil, nil`. Regression: extend internal/builder/enum_codec_test.go's existing `writeEnumCodecFixture`/`Run`/`assertOwnerCollisionSentinels` harness (already proves no-partial-write for four other failure modes) with the pointer-field WithEnum case, sibling to the existing slice/WithStringerEnum test at line 71-79.

correction: Mid-implementation the manager/user narrowed scope twice: (1) reject any speculative checks, edge-case defenses, or new validation machinery beyond the one reproduced bug — keep any CLI-subprocess proof tied to the same fixture or omit it if the existing Run-path proof already covers artifact safety; (2) final decision: this pointer-WithEnum case does not block correct use, it's a small consistency/diagnostic improvement, not a release-blocking correctness fix — implement only the one error branch plus the one existing-harness sentinel regression, do not add a CLI subprocess fixture or any further machinery. I had drafted a CLI-subprocess regression (build the real gen-jsonschema binary, run it via testutils.RunCommand against the same fixture) before the second correction landed; removed it entirely per the final decision rather than leaving partial/unused scaffolding.

result: Implemented exactly the bounded fix from research.md. `internal/builder/gen_schema.go` `resolveEnumFieldPlan`: collapsed the `config.UseStringer` / non-stringer split into a single `fmt.Errorf` (previously the non-stringer `WithEnum` branch was `return nil, nil`, silently dropping the field to render as a plain integer). Added `TestEnumRejectsPointerFieldBeforeWriting` to internal/builder/enum_codec_test.go: a `*Color` field registered with plain `jsonschema.WithEnum` now fails `Run(BuilderArgs{...})` with "supports only a direct named enum, Optional[E], or Nullable[E]" and `assertOwnerCollisionSentinels` confirms pre-seeded `jsonschema/Owner.json`/`jsonschema_gen.go` are untouched (byte-identical) after the failing run. Diff is two files, 11 insertions / 4 deletions total — no new validation phase, no new option kind, no new Go-shape support.
verify: `gofmt -l` clean on both changed files. `go test ./internal/builder/... -run 'Enum' -v`: all 8 enum tests pass including the new one. `go test ./...`: full suite green across every package (root, gen-jsonschema, internal/builder incl. all basic_test.go golden-file comparisons — proving existing artifacts remain byte-identical, internal/syntax, internal/typegrammar, internal/typescript, all examples/*).

review: Independent bounded review found no defect in the implementation. It suggested adding checksum-sentinel coverage; manager rejected that as speculative expansion because the changed declaration-analysis path returns before rendering and the existing sentinel harness already proves the principal schema and generated-code outputs are untouched.
