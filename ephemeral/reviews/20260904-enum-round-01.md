# Adversarial review: issue #58 enum codecs

## Scope and sources

Reviewed the complete origin/main...ef2ed9f implementation in the issue-58 worktree, including generator, scanner, templates, tests, examples, documentation, and the fresh consumer proof. Compared behavior with ephemeral/github/issue-58.md, docs/spec/v1.md (generated-method ownership and #58 enum decisions), and the repository build-tag guidance. The independent consumer transcript is v1-wave2/ephemeral/wave2/enum-consumer-proof.txt.

## Verdict

**NO-GO.** The fresh consumer demonstrates the intended direct, Optional, Nullable, and mixed union field-specific roundtrips, but generation still has three contract failures below. The first two can produce an artifact whose schema and Go wire behavior disagree; the third makes the generator reject valid generation-only stubs under a reserved-tag environment.

## Findings

### [P1] Typed enum aliases in separate const declarations are silently omitted

**Evidence:** internal/syntax/scan_result.go:451-477 resets lastTypeName for every const declaration and only records an untyped constant when an earlier typed constant exists in that same declaration. The field-registration fallback repeats the same declaration-local rule in internal/builder/gen_schema.go:695-724 (discoverEnum). go/types still gives const ColorAlias = ColorRed the named enum type, but the syntax filters discard it when it is in its own declaration.

**Impact:** With type Color int, const ColorRed Color = 1, and a separate const ColorAlias = ColorRed, a WithStringerEnum field resolves only ColorRed. A unique alias is absent from the generated schema and decoder; an alias with the same underlying value is not rejected as the ambiguous string-mode registration required by issue #58 and docs/spec/v1.md:95. This violates the acceptance requirement to resolve aliases and duplicate underlying values before writing output. Existing tests cover duplicates in one const block, so they do not exercise this declaration boundary.

**Required correction:** Build the enum set from resolved typed constant objects, or otherwise carry typed expression aliases across declarations, then apply the existing duplicate-value policy to every declared constant before rendering or writing.

### [P1] json:",string" is accepted despite being outside the v1 mapping contract

**Evidence:** internal/builder/gen_schema.go:1681-1687 validates only the Optional omitzero requirement; it does not reject the string JSON option on a registered enum. Integer WithEnum fields have a numeric schema and no adapted owner codec (gen_schema.go:1488-1490), so the alias field retains json:",string" and encoding/json emits a quoted number. The schema path uses the numeric enum values from the registration. For WithStringerEnum, the generated wrapper copies the original tag to its json.RawMessage field (internal/builder/schemas.go.tmpl:169-179,244-253); the standard encoder does not apply primitive string quoting to RawMessage, so the option is silently ignored while the adapter emits constant-name strings.

**Impact:** A registered integer field such as Value Color with tag json:"value,string" and WithEnum generates a numeric schema but encodes "value":"1", failing the issue-58 schema-valid encoding boundary. With string mode, the same source tag silently changes meaning from the ordinary Go JSON contract instead of producing an explicit unsupported-mapping diagnostic. The v1 matrix explicitly excludes json:",string" mappings (docs/spec/v1.md:46) and requires unsupported combinations to be diagnosed, while the current generator succeeds.

**Required correction:** Reject json:",string" for registered enum fields before any output is written, or define and prove a separate mapping that preserves both schema and registration semantics. The accepted v1 contract currently calls for rejection.

### [P2] Reserved jsonschema build tag can turn generation stubs into false production collisions

**Evidence:** internal/syntax/json_methods.go:22-53 excludes _test.go and jsonschema_gen.go, but relies on IsProductionGoFile to exclude schema.go. IsProductionGoFile (json_methods.go:100-120) starts with build.Default and adds every GOFLAGS tag, including the reserved jsonschema tag; it never removes that tag or otherwise recognizes the generation-only declaration file. Under GOFLAGS=-tags=jsonschema, a schema.go stub such as func (Owner) MarshalJSON() ... { panic("not implemented") } matches and is reported as handwritten production by validateOwnerCodecMethods (gen_schema.go:500-565).

**Impact:** The repository contract says the jsonschema declaration stubs and !jsonschema generated production methods are mutually exclusive, and specifically says a generation-only declaration stub is not an owner collision (docs/spec/v1.md:80-82; shipped skill build-tag model). The current collision audit rejects valid generation input when the reserved tag is present in the process environment. The existing positive test exercises the default environment only and does not cover the reserved-tag case.

**Required correction:** Use the generator explicit generation/production build context and exclude the reserved generation tag from production-hook discovery, while still honoring supported custom production tags.

## Confirmed passing scope

The supplied fresh consumer proof passes repeated deterministic generation, schema-valid direct/Optional/Nullable string-mode roundtrips, numeric mode for the same Go enum type, ordinary string-backed enums, escaped enum values, unknown-name/numeric/null rejection, undeclared-zero rejection, owner transactionality, and mixed union/enum owner composition. The implementation also has focused generator tests for duplicate values in one declaration, unsupported containers, custom enum hooks, and owner collisions. These passes do not cover the three boundaries above.
