## Findings

### [Issue] Pointer-only `MarshalJSON` hooks on ordinary nested fields can be lost

The generated owner method is a value receiver and passes a value wrapper to
`json.Marshal`: `internal/builder/schemas.go.tmpl:169-177, 215`. An ordinary
nested field whose only custom encoder is `func (*T) MarshalJSON` is therefore
not addressable while the wrapper is encoded, so encoding falls back to T's
struct representation. This changes the behavior of a pointer owner as well:
the generated value receiver copies the owner before encoding. The supplied
reproduction at
`v1-wave2/ephemeral/wave2/pointer-hook-consumer` demonstrates the failure:
`TestOrdinaryPointerHook` expects `PointerHook.MarshalJSON` to run, but
`GOFLAGS=-p=2 go test ./... -run TestOrdinaryPointerHook -count=1` reports
`pointer hook calls=0` and emits `{"custom":{"value":"sentinel"},...}`.
That can make generated output fail the ordinary field's schema and violates
issue #57's “preserve ordinary field encoding” requirement and the contract's
custom-hook boundary (`docs/spec/v1.md:57-59, 89`). The current fixture tests
only value-receiver ordinary hooks (`test_run/test13-union-codec/types.go:84-92`).
The owner wrapper needs an explicit addressability strategy, or this hook shape
must be rejected/marked unknown before claiming support, with regression proof
for both owner value and pointer calls.

### [Issue] Legacy helper names collide for same-named interfaces from packages with the same package name

Legacy interface helpers are named only from `TypeSpec.Pkg().Name` and the
interface name (`internal/builder/gen_schema.go:1805-1814`). `RenderGoCode`
deduplicates by that name (`:1188-1192`). Two supported imported interfaces
such as `a/events.Event` and `b/events.Event` (both package name `events`) can
therefore either cause duplicate generated function declarations or cause the
second field to call the first interface's helper. The generated helper's
parameter type is the first interface (`internal/builder/schemas.go.tmpl:302,
334`), so this is a generated-consumer compile failure or an incorrect codec,
with no generation diagnostic. The v1 field alias includes owner/field context,
but the legacy path remains affected even though #57 explicitly requires
legacy registration support and helper reuse to be configuration-safe. Helper
keys should include the resolved package path (or a collision-safe hash) while
still reusing helpers for the exact same interface/configuration.

### [Issue] A null discriminator is accepted when the registered wire value is empty

`__jsonschema__marshalUnionObject` unmarshals an existing discriminator into a
Go string and only compares the resulting value
(`internal/builder/schemas.go.tmpl:379-386`). Go's JSON decoder accepts `null`
when decoding into `string`, leaving `""`. With a legal registration such as
`Impl("", Created{})`, a concrete hook returning `{"type":null,...}` therefore
passes the comparison and is emitted. The contract explicitly requires null
and non-string discriminator payloads to be rejected
(`docs/spec/v1.md:71, 82-86`), and the implementation currently claims that in
the parent docs. Decode has the same null-to-empty weakness at template lines
351-352 if an empty discriminator is registered. Check the raw token's JSON
kind (or require a successful non-null string token) before comparing, and add
an empty-wire-value regression case.

## Proof gaps / nitpicks

- The generated union fixture and fresh consumer validate generated output,
  and the fixture exercises a manually supplied replacement input, but neither
  asserts `ValidateJSON(input)` before the valid-input decode/encode/decode
  case. The acceptance text asks for valid input documents to survive; adding
  that assertion would bind the proof to both schema validity and typed
  decoding.
- `TestBasic` idempotence compares the second `jsonschema_gen.go` only
  (`internal/builder/basic_test.go:84-94`); it does not compare every generated
  schema/checksum file. This is useful evidence for method stability, but the
  issue's “repeated generation produces no changes” claim would be stronger
  with a complete generated-tree comparison.
