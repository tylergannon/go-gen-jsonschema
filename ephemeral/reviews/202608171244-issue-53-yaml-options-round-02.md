## Findings

### 1. The round-01 remediation breaks the documented transactional guarantee: a failed YAML decode now mutates the caller's data in place. (critical)

`internal/builder/schemas.go.tmpl:226-236`:

```go
func (n *Node) UnmarshalYAML(node *yaml.Node) error {
	data, err := __gen_jsonschema_yamlNodeToJSON(node)
	if err != nil { return err }
	next := *n                          // <-- shallow copy: aliases slices, pointers, maps
	if err := json.Unmarshal(data, &next); err != nil { return err }
	*n = next
	return nil
}
```

`next := *n` is a **shallow** copy. Slice headers, pointers, and maps in `next`
still reference the receiver's memory, and `encoding/json` deliberately decodes
*in place* into an existing slice's backing array and into an existing pointer's
target. So a decode that fails on a later field has already overwritten data
reachable from the untouched destination — and from any other holder of that
slice or pointer.

This contradicts issue #53's Expected bullet "Receiver assignment remains
transactional", `llms.txt:283-285` ("assigns the destination only after the
entire value decodes successfully"), and the guarantee the branch's own
`TestOptionalInterfaceDecodeIsTransactional` / rollback cases assert.

**Reproduction A — slice backing array** (`/tmp/yprobe2`, generated by the
working-tree CLI with `--formats=both --validate`, type
`Node{Tags []string \`json:"tags"\`; Count int \`json:"count"\`}`):

```go
original := Node{Tags: []string{"keep-a", "keep-b"}, Count: 5}
shared := original.Tags        // a reference the caller still holds
got := original
err := yaml.Load([]byte("tags:\n  - clobbered\ncount: not-an-int\n"), &got, yaml.WithV4Defaults())
// err  = yaml: construct errors: line 1: json: cannot unmarshal string into Go struct field Node.count of type int
// got  = Node{Tags:[]string{"clobbered", "keep-b"}, Count:5}   <-- destination mutated on a FAILED decode
// shared = []string{"clobbered", "keep-b"}                      <-- caller's own slice mutated
```

**Reproduction B — pointer target** (`/tmp/yprobe3`, `--formats=both`, type
`Node{Inner *Inner; Count int}`):

```go
inner := &Inner{A: "keep-a", B: "keep-b"}
got := Node{Inner: inner, Count: 1}
err := yaml.Load([]byte("inner:\n  a: clobbered\ncount: not-an-int\n"), &got, yaml.WithV4Defaults())
// err   = json: cannot unmarshal string into Go struct field Node.count of type int
// *inner = Inner{A:"clobbered", B:"keep-b"}   <-- caller's pointee mutated despite the error
```

**Impact:** generated code silently corrupts caller-visible state on the error
path — the failure mode `ValidateYAML`-then-`Unmarshal` workflows are least
prepared for, since the error looks like a clean rejection. Note the scope: union
owners are *accidentally* immune because their generated `UnmarshalJSON` decodes
through a zero `Wrapper`/`Alias` and never writes into the receiver's memory
(`v1_interfaces_options/jsonschema_gen.go.golden:161` onward). The exposed class
is **plain registered types with no interface fields** — the README's `Person`
shape, i.e. the most common consumer.

There is a real design tension here that the branch has not yet resolved: `next
:= *r` buys `encoding/json` merge semantics at the cost of transactionality;
`var next T` (round-01 state) buys transactionality at the cost of merge
semantics. The branch now advertises **both** and delivers merge with broken
transactionality. Either pick merge and correct the transactionality claim in
`llms.txt`/`README.md`, or keep the guarantee and make the temporary
independent of the receiver's memory (e.g. decode into a zero value and restore
only the fields the document omitted, or round-trip the receiver through JSON
before merging — the latter is cheap because the payload is already JSON here).

### 2. The regression test added for the round-01 fix cannot detect finding 1, because it only exercises a type immune to the code path it tests. (issue)

`internal/builder/testfixtures/v1_interfaces_options/optionality_test.go:64-86`
(and the identical `test_run` copy) adds the pre-populated-receiver case
exclusively against `Owner`:

```go
prepopulated := Owner{IF: ..., IFaces: []IFace{Impl2{Y: 7}}, Label: ..., Timeout: ...}
yamlGot := prepopulated
yaml.Load(..., &yamlGot, yaml.WithV4Defaults())
jsonWant := prepopulated
json.Unmarshal(..., &jsonWant)
reflect.DeepEqual(yamlGot, jsonWant)
```

`Owner` has a generated `UnmarshalJSON`, so `next := *o` never actually feeds
stock `encoding/json` merge behavior — the assertion passes for the
`__next.IFaces = o.IFaces` fallback only, which is the one path the worklog's
`review_decision` scoped to. The whole class of registered types **without**
interface fields — where stock merge semantics and the in-place aliasing both
live — has no YAML decoding coverage anywhere in the repo; every YAML fixture in
`internal/builder/` is a union owner. `unmarshal_formats_test.go` checks only
that symbols are present/absent, never runtime behavior.

**Impact:** the test suite reports green while generated code for the most common
consumer shape corrupts data (finding 1). A fixture with a plain registered
struct carrying a slice and a pointer field, decoded from a pre-populated
receiver both successfully and with a mid-document type error, would close the
gap.

### 3. `ValidateYAML` and `UnmarshalYAML` can interpret the same document under different YAML dialects. (nitpick — carried from round 01, unaddressed)

`schemas.go.tmpl:51-57` hardcodes `yaml.WithV4Defaults()` inside
`__gen_jsonschema_yamlToJSON` (used by `ValidateYAML`), while
`__gen_jsonschema_yamlNodeToJSON` (used by `UnmarshalYAML`) inherits whatever the
caller passed to `yaml.Load`/`yaml.Unmarshal`. Legacy `yaml.Unmarshal` still
decodes generated types successfully (verified in round 01), so validate-under-v4
then decode-under-v3 is reachable in exactly the workflow the README recommends.
Documenting that YAML entry points assume v4 resolution would be enough.

### 4. Translation failures surface raw `encoding/json` internals. (nitpick — carried from round 01, unaddressed)

A non-string YAML mapping key yields
`yaml: construct errors: line 1: json: unsupported type: map[interface {}]interface {}`.
The behavior matches the documented rule ("YAML constructs that cannot be
represented by JSON are rejected") but the message names a Go type the user never
wrote and does not identify the offending key. Wrapping the `json.Marshal` error
in `__gen_jsonschema_yamlNodeToJSON` (`schemas.go.tmpl:42-48`) would make the
documented rule discoverable.

### 5. Documentation of the YAML naming/strictness boundary is incomplete in two places. (nitpick)

- The registration boundary is still unstated: because `UnmarshalYAML` is
  generated per registered type, a document decoded into an *unregistered* outer
  struct resolves outer keys by yaml/v4 rules and inner registered-type keys by
  JSON Schema property names — two conventions in one file, no diagnostic. Round
  01 raised this; unaddressed.
- The new `WithKnownFields` limitation was added to `README.md`, `llms.txt`, and
  `SKILL.md`, but **not** to the website, whose YAML paragraph
  (`website/src/content/docs/guides/validation-ci.md:49-52`) covers the same
  ground and is the published surface.
